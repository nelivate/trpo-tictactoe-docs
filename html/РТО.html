1. Введение

Руководство по техническому обслуживанию определяет порядок периодических проверок, диагностики, обновления и восстановления программного комплекса «Крестики и нолики». Обслуживание выполняется администратором или назначенным техническим специалистом. Документ составлен в соответствии с ГОСТ 19.508-79.

Объект обслуживания: Docker-стек (контейнеры server и db), клиентские приложения Flutter, сетевое окружение и резервные копии. Цель обслуживания — поддерживать доступность сервера, целостность данных и работоспособность игровых сессий.

Обслуживание не включает изменение игровых правил и вмешательство в ход партий. Все работы, влияющие на доступность, выполняются в согласованное время с предварительным уведомлением пользователей.

2. Общие указания

Техническое обслуживание проводится без остановки игрового процесса, если это возможно. Работы, требующие остановки контейнера server или db, выполняются в согласованное время; пользователи уведомляются заранее. Перед обновлением и восстановлением создаётся резервная копия базы данных.

К обслуживанию допускается специалист, знакомый с Docker Compose, командной строкой, PostgreSQL и журналами приложения. Изменения конфигурации фиксируются в формуляре и журнале сопровождения.

3. Требования к техническим средствам

Серверный хост: Windows 10/11 с Docker Desktop (Linux-контейнеры) или Linux с Docker Engine; процессор не менее 2 ГГц, ОЗУ не менее 4 ГБ, свободное место не менее 3 ГБ для образов, тома pgdata и резервных копий. Клиентские компьютеры: Windows 10/11, ОЗУ не менее 2 ГБ, свободное место 50 МБ. Сеть: TCP/IP, открытый порт 5000.

Программное обеспечение: Docker Engine 24+ и Docker Compose v2, PostgreSQL 15+, .NET 10 Runtime в контейнере server, Flutter-клиент в release-сборке. Дополнительные библиотеки на клиентских компьютерах не требуются.

4. Описание функций

Контейнер server принимает TCP-соединения, выполняет авторизацию, управляет игровыми сессиями, проверяет ходы, фильтрует чат и рассчитывает баллы. Контейнер db хранит профили, сессии, результаты и сообщения. Клиент Flutter отображает интерфейс и отправляет команды; сервер остаётся единственным источником истины.

Обслуживание охватывает доступность контейнеров, целостность базы, актуальность резервных копий, сетевую доступность порта 5000 и работоспособность клиентских приложений.

7. Обновление программного обеспечения

Порядок обновления:

  1. Согласовать окно обслуживания и предупредить пользователей.

  2. Сделать резервную копию базы данных и файлов сервера.

  3. Остановить контейнеры (docker compose stop).

  4. Получить новую версию файлов и выполнить docker compose up -d --build.

  5. Схема базы применяется автоматически при старте сервера.

  6. Запустить сервер и проверить журнал.

  7. Провести контрольную партию с тестовыми учётными записями.

  8. Зафиксировать версию и изменения в формуляре.

При обнаружении критической ошибки выполняется откат: остановить сервер, вернуть предыдущие файлы и восстановить базу из резервной копии. Откат оформляется записью в журнале обслуживания.

8. Резервное копирование и восстановление

Ежедневная копия базы данных:

docker compose exec -T db pg_dump -U ttt -d ttt -F c > backup.dump

Проверка копии восстановлением на тестовую базу:

docker compose exec -T db pg_restore -U ttt -d ttt -c < backup.dump

Копии хранятся на отдельном носителе не менее 14 дней, полные копии — до трёх месяцев. Раз в месяц обязательно проверяется восстановление. Если копия не восстанавливается, создаётся новая и выясняется причина.

Перед обновлением и после значимых изменений создаётся дополнительная копия. Файлы копий защищаются от несанкционированного доступа.

9. Проверка после обслуживания

После любых работ выполняется контрольный набор проверок:

  1. Сервер запущен, порт доступен, журнал без ошибок уровня error.

  2. Контейнер db здоров, база открывается, таблицы на месте.

  3. Тестовый игрок проходит авторизацию.

  4. Создаётся сессия, подключается второй игрок.

  5. Выполняется ход, поле синхронизируется у обоих клиентов.

  6. Отправляется сообщение чата, фильтр работает.

  7. Партия завершается, результат и баллы сохраняются.

  8. Резервная копия создаётся и восстанавливается.

Результаты проверок заносятся в журнал обслуживания. При отрицательном результате работы не считаются завершёнными до устранения причины.

11. Хранение и учёт

Все работы по обслуживанию фиксируются в журнале: дата, исполнитель, вид работ, результат, обнаруженные дефекты и принятые меры. Журнал хранится вместе с эксплуатационной документацией.

Резервные копии и журналы относятся к служебной информации. Доступ к ним предоставляется только администратору и руководителю проекта. Устаревшие копии уничтожаются после истечения срока хранения.

Плановое обслуживание проводится не реже одного раза в месяц. Внеплановое — при сбоях, обновлениях и изменениях конфигурации сети.
